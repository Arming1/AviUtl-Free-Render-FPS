# Phase 2 架构方案比较

## 当前推荐

优先继续调查方案 B 的最小前置条件：定位“整数场景帧/对象帧写成 `OBJECT_INFO.time`”的内部构造点，并先做只记录、不修改的动态验证。

方案 A 单独无法实现真 30→60，因为已确认输出调度与私有 getVideo 桥都只携带整数帧。方案 C 可能提供最完整的自由时间能力，但目前连可靠场景渲染签名、线程要求和资源上下文都没有恢复。方案 D 影响范围最大，只适合作为 B/C 都失败后的最后私有 Hook 方向。

本阶段不选择任何方案进入实现；下面是建立在现有证据上的设计比较，不是功能已可行的声明。

## 比较总表

| 维度 | A. Hook 输出渲染循环 | B. Hook 时间轴求值，临时替换当前时间 | C. 直接调用内部场景渲染函数 | D. 导出期全局修改“帧→时间”转换 |
|---|---|---|---|---|
| 真子帧能力 | 单独不具备 | 理论上具备，待找到写入点 | 理论上最强，待恢复时间参数 | 理论上具备，但可能仍被整数缓存截断 |
| 实现难度 | 中 | 高 | 极高 | 极高 |
| 稳定性 | 中；边界较清晰 | 中低；依赖私有求值状态 | 低；需重建完整上下文 | 低；影响全局行为 |
| 插件兼容性 | 较高，但只能整数采样 | 不确定；第三方效果可能读取 frame 而非 time | 不确定；需复现正常宿主环境 | 最低；所有插件和预览都可能受影响 |
| 缓存正确性 | 整数缓存一致，但无法表达子帧 | 高风险；必须把子帧时间纳入 key/失效 | 高风险；需显式管理所有缓存 | 极高风险；旧整数 key 可能污染所有路径 |
| 音频同步 | 仍按原有整数时间 | 必须设计独立音频时间映射 | 必须同时调用/同步音频渲染 | 会改变全局音频换算或导致 A/V 分裂 |

| 可重入性要求 | 低到中 | 高；必须支持嵌套恢复 | 极高 | 极高 |
| AviUtl2 更新维护成本 | 中 | 高 | 最高 | 最高 |
| 当前证据成熟度 | 高，但能力不足 | 有运行时方向，地址未知 | 只有类名/工作器线索 | 只有概念与设置线索 |
| 当前建议 | 仅作为调度/追踪外壳 | **首选研究方向** | 远期备选 | 最后备选 |

## 共同时间映射

若未来找到真正的时间入口，输出采样应使用明确的有理映射，而不是修改编码器元数据：

```text
output_index k
  -> target_time = k * output_scale / output_rate
  -> timeline/object/effect evaluation at target_time
  -> one newly rendered image
```

例如工程 30 FPS、输出 60 FPS：

```text
k=0 -> 0
k=1 -> 1/60
k=2 -> 2/60 = 1/30
k=3 -> 3/60
...
```

对于非整数倍速率，内部表示必须保持有理数或足够稳定的时间标识；直接把 double 当唯一缓存 key 容易受舍入影响。

## 方案 A：Hook 输出渲染循环，改变输出帧调度

### 可能落点

- 输出服务入口：`aviutl2.exe+0x1EE280`
- 输出开始/状态初始化：`aviutl2.exe+0x225AE0`
- getVideo 宿主桥：`aviutl2.exe+0x22A6C0`
- 私有整数视频工作器：`aviutl2.exe+0x2206B0`

### 优点

- 输出生命周期和开始/结束边界相对容易识别。
- 可以维护独立的 `output_index`、进度和目标输出帧数。
- 可作为 B 或 C 的外层调度器。

### 根本限制

`OUTPUT_INFO::func_get_video`、`0x22A6C0` 和 `0x2206B0` 当前都只携带整数位置。把 60 个输出请求映射到 30 个工程帧，只能重复某些整数帧；这违反“真实时间采样”要求。

因此 A 不能单独成功。它只有在 B/C 已能按 `target_time` 生成新画面时才有价值。

### 主要风险

- 原输出范围 `n`、进度、终止和插件期望可能不一致。
- x264guiEx 等插件直接把 `oip->n/rate/scale` 写入编码器参数；外层必须防止元数据与实际采样数分裂。
- Hook 共用 getVideo 桥可能同时影响预览、缓存预取和其他输出插件。

## 方案 B：Hook 时间轴求值过程，临时替换当前时间

### 理想落点

理想点位于：

```text
整数场景位置已进入
  -> [在这里构造可替换的场景/对象时间]
  -> 动画、对象、效果读取该时间
  -> 合成
```

当前中性名称为 `TimelineEvalCandidate_B`。它必须早于对象动画和效果求值，也必须晚于输出/预览请求的线程调度，才能限定改写作用域。

### 支持证据

- `OBJECT_INFO` 同时携带 `int frame` 与 `double time`（`reference/aviutl2_sdk/filter2.h:328-334`）。
- 实测对象回调发生在 `func_get_video` 返回前，且 `time=frame*scale/rate`。
- 公开查询接口接受 `double offset`（`reference/aviutl2_sdk/filter2.h:421-431`），说明对象求值层至少能表达秒偏移。

### 尚缺证据

- `time` 是临时结构字段、线程局部状态，还是更早的全局值。
- 动画脚本和内置效果最终读取 `frame` 还是 `time`。
- 把 time 改成 1/60 秒时，整数 frame 是否仍会让动画保持在 0 或 1/30。
- 缓存 key 是否包含分数时间。

### 实现原则

- 第一原型只记录原值，不修改。
- 真正修改时必须使用作用域式保存/恢复，并处理异常、早退、嵌套渲染。
- 不能只改一个 `double` 字段；必须先证明所有下游求值读取同一时间源。
- 子帧 ID 必须进入缓存键或强制安全失效，避免 `0` 与 `1/60` 命中同一帧缓存。

### 主要风险

运行时已确认输出线程和对象滤镜线程不同。一个无同步的全局覆盖会把其他预览/缩略图/并行对象渲染带到错误时间。第三方插件还可能只读取 `OBJECT_INFO.frame`，造成同一画面中不同效果使用不同时间基。

## 方案 C：直接调用内部场景渲染函数，并传入合成时间

### 理想能力

如果存在签名类似“场景上下文 + 时间 + 输出目标”的入口，C 可以完全绕过整数 getVideo 桥，为每个输出样本独立合成画面。它也是最容易在设计上明确缓存键和输出帧数的方案。

### 当前线索

二进制存在：

- `Render::RenderVideoWorker::renderingTargetObject`
- `Render::RenderVideoWorker::requestRenderingFrame::<lambda>`
- `RenderSection`
- `Render::RenderAudioWorker::createSceneAudioBlock`

但这些只是字符串/RTTI 线索。目前没有恢复一个接收 double 或有理时间的完整场景渲染签名。

### 必须解决的问题

- 上下文由谁创建、谁拥有，何时可用。
- D3D11 device/context、帧缓冲、场景锁和对象快照的生命周期。
- 函数必须在哪个线程执行，是否通过任务队列异步完成。
- 是否可重入；输出请求期间再调用是否会死锁。
- 如何获得与正常 getVideo 完全一致的颜色格式和后处理。
- 音频如何以同一目标时间区间渲染。

### 主要风险

即使函数入口正确，缺失一个锁、TLS、任务上下文或资源引用也可能造成间歇性崩溃或画面污染。其签名和内部布局也最容易随 AviUtl2 更新变化。

## 方案 D：导出期间全局修改“帧→时间”转换逻辑

### 思路

在输出开始时安装全局时间比例/分母，在输出结束时恢复，使所有 `frame -> time` 换算在导出期间按输出 FPS 解释。

### 潜在优点

- 如果 AviUtl2 的动画、效果、场景与音频都统一经过一个转换函数，覆盖范围可能最完整。
- 外层输出插件仍可使用原有 getVideo/合成路径。

### 主要问题

- 当前没有证据证明存在单一全局转换函数。
- 工程帧号、对象区间、关键帧、缓存和编辑 UI 大量使用整数帧；全局改变比例可能改变对象长度和关键帧语义，而不只是求值时间。
- 导出期间可能仍有预览、缩略图、后台音频等并行工作，它们会一起被改写。
- 异常或中止后恢复失败会污染后续编辑状态。
- 私有音频路径已经显示独立整数乘除；视频和音频未必共享同一转换点。

### 风险结论

D 是四种方案中作用域最广、兼容性最差的。没有证明“单一、线程局部、可恢复的转换点”前，不应制作原型。

## 缓存设计要求

无论 B、C 或 D，真子帧都必须把目标时间纳入缓存身份。建议未来用规范化有理数：

```text
TimeKey = reduce(output_index * output_scale, output_rate)
```

缓存键至少还需包含场景/对象版本、输出尺寸、像素格式和影响渲染的配置。若不得不复用 AviUtl2 的整数帧缓存，则必须证明可以在子帧调用前后安全失效，且不会破坏并发请求。

静态分析在 `0x2206B0` 下游看到 4 字节键哈希线索，这使“直接塞入两个同一整数帧内的子帧”存在明显碰撞风险；但尚未证明所有渲染缓存都采用该键。

## 音频同步要求

目标视频样本时间是离散点；音频则是连续区间。正确同步应分别定义：

```text
video sample k:  t = k / output_fps
audio interval:  [t_start, t_end) -> integer PCM sample range
```

不能简单把视频的 30→60 比例套在音频 sample index 上。`aviutl2.exe+0x220D60` 显示音频路径有独立的整数换算和工作器；在字段语义与舍入方式恢复前，任何改写都可能产生一帧边界误差或长期漂移。

## 更新与特征码策略

未来若进入 Hook 原型，必须同时满足：

- 校验目标 `aviutl2.exe` 的 SHA-256 或受支持版本表。
- 以字符串 xref + 函数边界 + 多条关键指令/调用关系组合定位，不能只用短字节串。
- 特征匹配必须唯一；不唯一或语义校验失败时拒绝加载。
- 所有地址保存为模块相对 RVA，不保存某次运行的绝对地址。
- no-op 原型先证明调用次数、线程、嵌套深度和原值恢复，输出画面逐帧哈希必须与未 Hook 基线一致。

## 阶段决策

- A：保留为未来的输出调度外壳，单独淘汰。
- B：继续调查；这是最可能在不重建整个渲染器的情况下影响时间的方向。
- C：保留为高成本备选；先恢复可靠签名和线程模型。
- D：最后备选；除非证明存在单一可作用域化的转换点，否则不实施。
- 内部 Hook 原型：本阶段不制作，因为 `TimelineEvalCandidate_B` 尚未定位。
